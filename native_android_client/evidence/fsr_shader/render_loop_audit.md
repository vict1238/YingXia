# Windows libmpv render loop audit

The new Windows-only vendored plugin enables `MPV_RENDER_PARAM_ADVANCED_CONTROL` so libmpv can expose `vo-passes` performance descriptions/timings. This is an API integration change, not a shader flag. The source audit follows the bundled `include/render.h` threading contract and upstream mpv v0.36.0 [`render.h`](https://github.com/mpv-player/mpv/blob/v0.36.0/libmpv/render.h) and [`vo_libmpv.c`](https://github.com/mpv-player/mpv/blob/v0.36.0/video/out/vo_libmpv.c).

The original plugin used synchronous `mpv_get_property(video-out-params)` calls on the render worker and freed its GL surface before the mpv render context. Both are incompatible with the stronger advanced-control contract.

The modified integration:

- Moves initial normal core option calls onto the manager's independent creation thread, before its render context exists.
- Obtains output dimensions exclusively from `VideoOutputManager.SetSize`, supplied by the Dart metadata listener or explicit FSR render target. The renderer makes no ordinary core property/command calls. Before initial metadata, its texture is 1×1; leaving enhancement restores cached actual source dimensions through Dart.
- Installs the update callback immediately after context creation. The callback only queues a task. Every callback schedules `mpv_render_context_update` on the single render worker, with the original GL context current, including when paused/idle and no frame is pending. A callback arriving during another update queues another update. Only `MPV_RENDER_UPDATE_FRAME` or an explicit target resize redraws a frame.
- Keeps `SetSize`, GL resize, render update/render calls and renderer cleanup on that same worker. `SetSize` can redraw a paused current frame after servicing pending control dispatch.
- Marks destruction atomically, closes captured texture-callback lifetime guards, detaches the mpv update callback, and waits for the render-worker cleanup barrier. It frees the mpv render context while the original GL context is current, then releases ANGLE/texture resources. The no-texture path also executes cleanup.
- Completes the asynchronous Windows `Dispose` MethodChannel result only after actual renderer cleanup. The Dart player can therefore await render-context release before destroying its mpv core. The UI thread waits on no native renderer mutex.
- Exposes `VideoOutputManager.GetRendererBackend` on `com.alexmercerind/media_kit_video`, argument `{'handle': '<decimal native handle>'}`, returning `pending`, `hardware`, or `software`. The query uses a try-lock on a separate short-lived state registry and an atomic renderer state; it never waits on the core or render worker. A software renderer cannot execute FSR and is reported to the quality controller for fallback.
- Corrects the software API stride to `size_t`, as required by `MPV_RENDER_PARAM_SW_STRIDE` on Windows x64.
- Simplifies texture ownership to the single `ComPtr` reference returned by `CreateTexture2D`, released once via `Reset()`. The upstream extra manual `AddRef()` and explicit `Release()` pair was balanced overall; it was not a proven double release. Shared HANDLE export transfers no raw COM reference to Flutter/EGL, so the additional manual reference is unnecessary. Removing the extra `AddRef()` as well as the explicit `Release()` preserves the overall reference balance. Candidate 4's interim Reset-only change retained those extra references; it was superseded before final release to avoid a per-resize leak.
- Serializes ANGLE target resize/cleanup with the same mutex used by Flutter's D3D texture read and GL draw, so `CopyResource` cannot race retiring/replacing either texture. The mutex is released on resize exceptions, and read rejects null resources.
- Retires the previous texture ID and publishes each new ID together with its descriptor/variant map entries under `textures_mutex_`. Flutter Register/Unregister calls remain outside this mutex to allow synchronous callbacks. GPU and software callbacks capture their own registration ID, use `find`, and return null for unpublished/retired/missing IDs rather than throwing `map::at` exceptions across Flutter's callback boundary. Independently retained callback guards reject work after teardown starts. Teardown drains an already-running resize before taking its final texture ID.
- Retains an explicitly owned `ComPtr` lease of the old exported D3D texture until its Flutter unregister callback completes. A legacy shared handle's validity depends on the resource lifetime; this preserves the resource while Flutter may still import a descriptor already returned by an earlier callback. See Microsoft's [GetSharedHandle contract](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiresource-getsharedhandle). The lease is released on completion rather than retained indefinitely.
- Receives Create, SetSize and Dispose on a separate single-worker FIFO control queue. The MethodChannel handler only posts work and does not wait on the output mutex, rendering or core initialization. FIFO control receipt produces FIFO render-size posts; an old Enhanced target cannot enqueue after a later Off/source reset. Dispose runs after prior accepted size requests, drains/frees that output before replying, and a subsequent creation for a reused handle follows that disposal. Shutdown queues output cleanup after accepted controls and joins the control queue before the manager/render worker is destroyed. Ordinary core initialization remains on the independent control worker, never the render worker.

This document records source inspection. Candidate execution, actual `vo-passes` visibility, shader pass names, pause/resize/stop/replay and graceful exit are separate checks in the Windows runtime QA evidence. Integrated-GPU throughput is not inferred from this audit or the RTX 4060 shader pbuffer test.

Candidate 3 failed during the first source-size resize with native process exit `0xC0000409`; stdout recorded ANGLE hardware/advanced setup, a 1×1 initial texture and the start of the 1280×720 resize. No source sample or typed performance-property read had occurred. Inspection identified the definite resize/read synchronization gap and the opportunity to simplify balanced COM reference bookkeeping. Candidate 4 still failed at the same resize, so neither of those changes resolved the observed crash.

The owned-process debugger then captured the actual exception type `std::out_of_range`, a first-chance MSVC C++ exception followed by last-chance `0xC0000409` fatal-app-exit parameter 7 on the same thread. Its stack ran from MSVCP140 through `media_kit_video_plugin.dll` into Flutter's texture/raster callback. The proof is `evidence/windows/diagnostics/candidate4_debug_types/native_exception_stack.json`. This directly supports the texture ID/map publication race: the callback checked the old ID under a mutex, while resize mutated the shared ID outside that mutex and published a new ID before inserting its map entries. It could therefore execute `at(0)` or `at(new_unpublished_id)`. Candidate 5 replaces that path with the synchronized per-registration `find` callbacks described above. Successful candidate execution is recorded separately; the debugger proof concerns the pre-fix candidate.

The independent read-only review of Candidate 6 (`evidence/windows/native_readonly_review.json`) identified a separate P2: detached per-request SetSize threads could acquire the output lock in reverse receipt order. The channel returned success before native enqueue, so awaiting it in Dart did not order the actual render posts. Candidate 7 changes only the native manager's control scheduling to the FIFO described above; shader assets and Dart remain unchanged. `tools/native_control_queue_test.cc` compiles against the actual vendored ThreadPool and checks nonblocking receipt during delayed initialization, a delayed Enhanced target followed by Off, disposal before reused-handle creation, and 1,000 queued control/render operations in order. Its four scheduling checks pass in `control_queue_ordering.json`; they are isolated queue/lifetime checks, not a GUI or GPU playback claim. Actual final rapid-mode switching and final source-sized output are checked separately in runtime QA.

The follow-up independent review confirmed FIFO ordering and identified an adjacent shutdown-order issue: the plugin's dispatcher queue/mutex were declared after its manager, so implicit reverse member destruction could destroy the dispatcher before manager callbacks drained. Candidate 8 explicitly resets the manager at the beginning of the plugin destructor, while the dispatcher, channel and WindowProc are still alive; only after manager control/render cleanup completes does it restore the WindowProc and detach the plugin instance. Shader/Dart source and queue scheduling are unchanged by this exact destructor-order correction. Final close/startup runtime checks are recorded separately.
